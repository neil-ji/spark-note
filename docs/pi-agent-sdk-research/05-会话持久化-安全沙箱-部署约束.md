> **调研日期**: 2026-08-03

## 1. 会话持久化

### 1.1 存储架构

pi 的会话以 JSONL 文件持久化，默认存储在：

```
~/.pi/agent/sessions/--<cwd-path>--/<timestamp>_<uuid>.jsonl
```

- `<cwd-path>`：工作目录的绝对路径，`/` 替换为 `-`
- 每个会话是独立的 `.jsonl` 文件
- 支持"无会话"模式（`--no-session` 或 `SessionManager.inMemory()`），不写入磁盘

### 1.2 SessionManager API（SDK 控制）

```typescript
import { SessionManager } from "@earendil-works/pi-coding-agent";

// 持久化会话（默认行为）
const sm = SessionManager.create("/path/to/project");

// 内存会话（web 场景的临时会话）
const sm = SessionManager.inMemory();

// 继续最近会话
const sm = SessionManager.continueRecent("/path/to/project");

// 打开指定会话文件
const sm = SessionManager.open("/path/to/session.jsonl");

// Fork 会话（从已有会话创建新会话）
const sm = SessionManager.forkFrom(sourcePath, targetCwd);

// 列出会话
const sessions = SessionManager.list("/path/to/project");

// 列出全部会话（跨所有项目）
const allSessions = SessionManager.listAll();
```

### 1.3 自定义会话目录

通过 SDK 的 `agentDir` 配置自定义会话存储位置：

```typescript
const { session } = await createAgentSession({
  agentDir: "/data/pi-sessions/user-123",  // 每用户独立目录
  sessionManager: SessionManager.create("/path/to/project", "/data/pi-sessions/user-123"),
});
```

### 1.4 会话生命周期管理

| 操作 | API / 命令 | 说明 |
|------|-----------|------|
| 新建 | `SessionManager.create(cwd)` 或 `/new` | 创建空白会话 |
| 继续 | `SessionManager.continueRecent(cwd)` 或 `pi -c` | 继续最近会话 |
| 恢复 | `SessionManager.open(path)` 或 `/resume` | 选择历史会话 |
| Fork | `SessionManager.forkFrom()` 或 `/fork` | 从历史消息创建新会话 |
| Clone | `/clone` 或 `createBranchedSession()` | 复制活跃分支到新文件 |
| 删除 | 删除 `.jsonl` 文件 或 `/resume` 中 Ctrl+D | 优先使用 trash CLI |
| 导出 | `/export [file]` | 导出为 HTML |
| 命名 | `/name <名称>` 或 `--name` | 设置显示名称 |

### 1.5 对 web 多用户场景的影响

**关键问题**：默认会话目录 `~/.pi/agent/sessions/` 是全局的，多用户共享会产生冲突。

**解决方案**：

```typescript
// 方案 1：每用户独立 agentDir
function getUserSessionDir(userId: string): string {
  return `/data/pi-sessions/${userId}`;
}

const userSessionManager = SessionManager.create(
  `/data/user-projects/${userId}/spark-note`,
  getUserSessionDir(userId)
);

// 方案 2：内存会话 + 手动持久化
const sm = SessionManager.inMemory();
// 通过 sm.getEntries() 获取条目 → 自定义存储（如数据库）
// 恢复时通过自定义逻辑重建会话
```

**推荐**：方案 1（每用户独立 `agentDir`）——简单、可靠、与 pi 原生机制兼容。

## 2. 安全沙箱

### 2.1 关键事实：pi 无内置沙箱

> **官方原文**："A partial in-process sandbox would be easy to misunderstand as a security boundary" while still depending on the host shell, filesystem, package managers, credentials, and extension code.

pi **故意没有内置沙箱**，安全隔离完全依赖外部机制。

### 2.2 权限模型

- pi 以启动用户的权限运行
- 内置工具（read/bash/edit/write/grep/find/ls）拥有与用户相同的文件系统和 shell 权限
- 扩展（TypeScript 模块）**拥有完整系统权限**，可以执行任意代码
- 包安装、shell 命令、语言服务器、测试命令等——都以普通本地进程方式运行

### 2.3 项目信任模型

项目信任是一个**输入加载守卫**（input-loading guard），决定是否加载项目本地的 `.pi/` 资源：

| 信任状态 | 行为 |
|---------|------|
| `always` | 自动加载项目资源 |
| `ask`（默认） | 交互模式下提示用户 |
| `never` | 跳过受保护的资源 |

**触发信任检查的条件**：cwd 包含 `.pi/settings.json`、`.pi` 资源目录（extensions/skills/prompts/themes）、`.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`、项目 `.agents/skills`。

**注意**：`AGENTS.md` 和 `CLAUDE.md` 上下文文件**不受信任检查影响**（除非通过设置禁用上下文加载）。

**非交互模式的信任行为**：
- 无信任决策时，`"ask"` 和 `"never"` 忽略受保护资源
- `"always"` 信任它们
- `--approve`/`-a` 和 `--no-approve`/`-na` 可覆盖单次运行

**对 web 场景**：非交互模式（SDK 嵌入）下不会弹出信任提示。需在启动时通过 `defaultProjectTrust` 设置明确的信任策略。

```typescript
// 全局 settings.json
{
  "defaultProjectTrust": "always"  // 或 "never"
}
```

### 2.4 三种容器化方案

| 方案 | 隔离对象 | 隔离级别 | 适用场景 |
|------|---------|---------|---------|
| **Gondolin** | 内置工具 + `!` 命令 | 微虚拟机（QEMU） | 本地开发，宿主保留鉴权 |
| **Plain Docker** | 整个 pi 进程 | 容器 | 单用户本地隔离 |
| **OpenShell** | 整个 pi 进程 + 策略控制 | 策略化沙箱（本地/远程） | 多用户 web 部署 |

#### Gondolin（本地微虚拟机）

```bash
cp -R packages/coding-agent/examples/extensions/gondolin ~/.pi/agent/extensions/gondolin
cd ~/.pi/agent/extensions/gondolin && npm install --ignore-scripts
cd /path/to/project && pi -e ~/.pi/agent/extensions/gondolin
```

- 宿主当前目录挂载为 VM 内的 `/workspace`
- 覆盖全部内置工具，文件改动写回宿主机
- 鉴权留在宿主机（不在 VM 内暴露 API key）

#### Plain Docker

```dockerfile
FROM node:24-bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends bash ca-certificates git ripgrep
RUN npm install -g --ignore-scripts @earendil-works/pi-coding-agent
WORKDIR /workspace
ENTRYPOINT ["pi"]
```

```bash
docker run --rm -it \
  -e ANTHROPIC_API_KEY \
  -v "$PWD:/workspace" \
  -v pi-agent-home:/root/.pi/agent \
  pi-sandbox
```

- ⚠️ API key 进入容器
- 宿主机目录通过 bind mount 暴露
- 适合单用户可信环境

#### OpenShell（策略控制沙箱）⭐ web 多用户推荐

```bash
openshell gateway add <gateway-url> --name <name>
openshell gateway select <name>
openshell sandbox create --name pi-sandbox --from pi -- pi
```

- 策略化文件系统、进程、网络、凭据控制
- 远程 Kubernetes 网关适合弹性多租户
- **推理路由**：模型 API key 不进入沙箱（沙箱内代码调用 `https://inference.local`，网关注入上游凭据）

## 3. Web 多用户部署约束与建议

### 3.1 进程模型

```
┌──────────────────────────────────────────────────────────────┐
│  Web Server (Node.js)                                         │
│                                                               │
│  ┌──────────────────┐  ┌──────────────────┐                  │
│  │ User A Session   │  │ User B Session   │  ...             │
│  │ ┌──────────────┐ │  │ ┌──────────────┐ │                  │
│  │ │ AgentSession │ │  │ │ AgentSession │ │                  │
│  │ │ - sm: user-a │ │  │ │ - sm: user-b │ │                  │
│  │ │ - cwd: a/    │ │  │ │ - cwd: b/    │ │                  │
│  │ └──────────────┘ │  │ └──────────────┘ │                  │
│  └──────────────────┘  └──────────────────┘                  │
│                                                               │
│  选项 A: 每用户独立 AgentSession（同进程）                      │
│  选项 B: 每用户独立 pi 子进程（RPC 模式 + Docker/OpenShell）    │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 隔离维度

| 维度 | 选项 A（同进程 SDK） | 选项 B（子进程 + 容器） |
|------|:---:|:---:|
| **会话隔离** | ✅ 每用户独立 sessionManager | ✅ 进程天然隔离 |
| **文件系统隔离** | ⚠️ 需手动限制 cwd | ✅ 容器 bind mount |
| **网络隔离** | ❌ 共享宿主机网络 | ✅ 容器网络策略 |
| **凭据隔离** | ⚠️ 共享进程环境变量 | ✅ 容器级环境变量 |
| **资源限制** | ❌ 需外部限制（cgroups） | ✅ 容器资源限制 |
| **崩溃隔离** | ❌ 一个用户崩溃影响全部 | ✅ 子进程崩溃不影响其他 |
| **实现复杂度** | 低 | 高 |
| **性能** | 高（同进程） | 中（进程创建 + 序列化开销） |

### 3.3 推荐部署架构（分阶段）

**Phase 1（MVP，单用户/内部使用）**：选项 A

```typescript
// 简化实现
const sessions = new Map<string, AgentSession>();

async function getUserSession(userId: string) {
  if (!sessions.has(userId)) {
    const { session } = await createAgentSession({
      agentDir: `/data/pi/${userId}`,
      sessionManager: SessionManager.create(
        `/data/projects/${userId}`,
        `/data/pi/${userId}/sessions`
      ),
      cwd: `/data/projects/${userId}`,
      defaultProjectTrust: "always",  // 信任项目资源
    });
    sessions.set(userId, session);
  }
  return sessions.get(userId)!;
}
```

**Phase 2（多用户生产环境）**：选项 A + Docker 容器

```dockerfile
FROM node:24-bookworm-slim
# ... pi + 依赖
# 每用户一个容器实例
```

每个用户独立的 Docker 容器运行 pi SDK web 后端，文件系统、网络、凭据完全隔离。

**Phase 3（SaaS 级别）**：选项 B + OpenShell

需要严格的策略化安全控制时，使用 OpenShell 远程 Kubernetes 网关，每会话/每用户创建沙箱。

### 3.4 关键配置清单

```typescript
const webDeploymentConfig = {
  // 会话隔离
  agentDir: (userId: string) => `/data/pi/${userId}`,
  sessionDir: (userId: string) => `/data/pi/${userId}/sessions`,
  cwd: (userId: string) => `/data/projects/${userId}`,

  // 安全
  defaultProjectTrust: "always",  // web 场景无交互提示
  tools: ["read", "bash", "edit", "write"],  // 最小权限原则
  noTools: undefined,  // 或 "builtin" 禁用内置仅保留自定义工具

  // 资源限制
  compaction: {
    enabled: true,
    reserveTokens: 16384,
    keepRecentTokens: 20000,
  },

  // 扩展
  additionalExtensionPaths: [],  // 仅加载受信任的扩展
  extensionFactories: [],        // SDK 注入的扩展（无需文件系统）

  // 凭据
  // 使用 setRuntimeApiKey 而非环境变量（不持久化、按需注入）
};
```

### 3.5 提示注入风险

> **官方原文**："Prompt injection from repository files, comments, documentation, context files, or build output is expected local-agent risk and cannot be reliably prevented by pi."

**对 web 场景的影响**：
- 用户上传的内容可能包含提示注入 payload
- 如果用户可编辑项目文件（`.pi/` 下的 settings/skills 等），风险更高
- **缓解措施**：
  - 用户间 cwd 隔离（每用户独立项目目录）
  - 限制文件写入权限（read-only mount 用于共享资源）
  - 审查用户上传内容中的指令性文本
  - 在 `input` 事件中过滤已知注入模式

## 4. 总结

| 维度 | 评估 | 建议 |
|------|------|------|
| **会话持久化** | ✅ JSONL 格式完整，SessionManager API 完善 | 每用户独立 agentDir |
| **安全沙箱** | ❌ 无内置沙箱 | Phase1: 同进程+目录隔离; Phase2: Docker; Phase3: OpenShell |
| **权限模型** | ⚠️ 以用户权限运行，扩展拥有完整权限 | 最小工具集、信任的扩展来源 |
| **多用户隔离** | ⚠️ 需自行实现 | 每用户独立 cwd + agentDir |
| **凭据管理** | ✅ setRuntimeApiKey 不持久化 | 运行时注入，不写 auth.json |
| **提示注入** | ⚠️ 官方确认为预期风险 | 内容过滤 + 文件系统隔离 |
| **Web 部署** | ⚠️ 非设计目标，需自行适配 | 推荐 Embed SDK + 容器化 |

> **置信度**：会话持久化（高）、安全沙箱（高——官方明确无内置沙箱）、部署约束（中——需自行验证 Docker/OpenShell 方案与 SDK 模式的兼容性）。  
> **信息来源**：https://pi.dev/docs/latest/security、/containerization、/sessions、/session-format、/sdk
